Chaperone

An oversight agent for a one-person company. Every email, payment, upload and delete its AI workers attempt goes through one gate that allows it, holds it for the owner or blocks it, and logs why.

Overview

Agents that answer to someone. Five AI workers run a small studio, and a sixth, Chaperone, is the only one with authority over what leaves it.

I built it for Track 2 (AI Governance, Security and Decision-Making) of the QwenWork x Hashmeta AI One-Person Company Hackathon, on AvePoint's "Agents Watching Agents" starter kit. The story is Lumen Studio, a fictional design studio in Singapore whose owner, Mei, runs Marketing, Sales, Ops, Finance and Support agents. Each morning she gets a plain-words briefing, money first, and anything that needs her shows up once in an approval queue. Every number she sees traces back to a file.

What it does

One gate
Every worker action (send, pay, delete, upload, quote) goes through a single endpoint, or through a QwenWork hook at the tool boundary, and comes back ALLOW, HOLD_FOR_APPROVAL or BLOCK with the rule IDs and the quoted evidence.
Data sensitivity
Files are classified by what is in them, not their names, into public, internal, client-confidential or regulated, citing the line that decided it. A summary keeps the sensitivity of its sources.
Fact-checking
Outbound figures, dates and commitments are checked against the files about that client and shown as claimed versus on file, with file and line quotes. A figure that traces to no file counts as made up.
Payment controls
No invoice is paid twice, 24-hour totals per supplier catch a payment split to dodge the approval limit, the payee must match the invoice's issuer and the currency must be SGD.
Owner-only decisions
Only the signed-in owner can decide real queue items. Approvals are single-use and bound to the exact action, and visitors get a sandboxed demo mode.
Web app for Mei
Six tabs in plain words: Today, Live log, Approvals, Fact-check, Where files went and Scorecard, updated live.

How it works

  1. Classify. Text is normalised first (Unicode forms, zero-width characters, Cyrillic lookalikes) and encoded payloads are decoded, so a disguise cannot lower a file's level. A file it cannot read counts as regulated.
  2. Trace lineage. Rewrites and splits inherit their sources' level, files an agent read through the gate join its context, and a word-overlap check links many paraphrases to their originals.
  3. Check scope. The action is compared with the task record on file, never with what the agent says its task is. A request can narrow its scope but never widen it.
  4. Fact-check. Every outbound figure has to match a file about the recipient's organisation.
  5. Add up payments. Duplicates, split payments, payee and currency are checked across all runs.
  6. Scan for injection. Email and file text is treated as data, not instructions. An agent that has read a flagged file has its later pay, upload and quote actions held for the owner.
  7. Apply the policy and log it. 19 rules decide the outcome, and the agent, action, files, level, rules and evidence go into an append-only log where each entry is chained to the last by SHA-256.

Of the 19 rules, 7 allow, 8 hold for the owner and 4 are never allowed. An action it does not recognise is held, never allowed. It runs on Node.js with no runtime dependencies and no API keys, streams to the web app with server-sent events and is deployed on QwenWork Pages.

Decisions and trade-offs

  • Fail closed. Unknown actions, unknown parameters and unreadable files are held or blocked, not let through. Every recipient field and attachment is checked, so nothing can hide in a field the gate did not expect.
  • Some rules no one can approve. The 4 never rules cannot be released from the queue, and a message claiming to be from Mei is quoted as evidence, never treated as her approval.
  • Approvals are bound to the action. Approving one email never releases a different email with the same opening line, and a retry after approval gets a fresh queue item.
  • One queue entry per item. Mei is never asked twice, and each agent is capped at 20 pending items an hour so one agent cannot flood the queue for the others.
  • Written for the owner. The app uses plain words and large type, and rule IDs appear only in the details lines.

Evidence

Classifier
30 of 30 files matched the ground truth: the kit's 27 plus 3 I added.
Scenarios
10 scenarios each scored on the decision, the rule IDs and the evidence: 15/15 on the kit's five and 15/15 on five I added, including a split payment, a fake owner approval and a prompt injection hidden in a vendor email.
Red team
QwenWork agents ran 107 attacks against the engine. 40 were held or blocked at first; after the fixes, 100 are, checked against the same harness.
Live agents
Through the QwenWork hook, a live sales agent emailing the client list outside was blocked and an ops agent deleting records was held for the owner.
Tests
173 of 173 unit tests pass, including adversarial regressions, and CI runs them on Node 18, 20 and 22.
Limits of these numbers

The classifier files and scenarios come from the starter kit plus ones I wrote, not an independent benchmark, and 7 of the 107 red-team attacks still get through. Injection detection is pattern-based, so new phrasings or languages can slip past it, and paraphrase detection misses translations and thorough rewrites. The hash chain shows tampering but does not prevent it, live state is held in memory and is lost on restart, and the gate only checks agents that are routed through it.

How I built it

I built the gate, the policy engine, the web app and the test harness as a full-stack developer, and used QwenWork agents for the rest. They produced the 174-second demo video (script, Kokoro narration, word-level captions from faster-whisper and Playwright footage of the running app), generated its music and title art, and ran the red team whose results drove the fixes.
