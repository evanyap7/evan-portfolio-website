Case study · Autonomous Trading Agent · Python

I built an LLM trading agent, measured it, and deleted the LLM.

The agent trades a small Webull Singapore account on its own, and no model can size or place an order. I tested whether Claude made it better than a plain momentum rule. It did not, so the LLM layer is gone.

The short version

  • What I built. An autonomous swing-trading agent where a model may only propose. Deterministic code verifies, sizes and risk-checks every idea, and an append-only ledger records each step.
  • What I tested. Claude agents (Haiku 4.5 screening, Opus 5.5 proposing) against a free, rule-based momentum baseline, both run through identical verification, sizing, stops and kill switch.
  • What I found. No measurable edge. The LLM cost about $27 a year on a $1,500 account and did not beat the baseline on the rule I had set. I removed it.
  • The uncomfortable part. Neither strategy beat simply holding the S&P 500 in 2024. I report that as the result.

The problem

I wanted a system that could run unattended without my having to trust a language model with money. Models are fluent and sometimes wrong, so the design question was not "how smart can the agent be" but "how bad can a failure get, and how fast can I see it."

How it is built

The only step that is not deterministic code is the one that proposes a trade. Everything before it is data, and everything after it is a gate.

1 · Research, after the US close

  1. Evidence
  2. Agent proposes
  3. Verifier
  4. Sizing
  5. Risk engine
  6. Queue

2 · Execute, 09:45 New York time

  1. Fresh quotes
  2. Re-verify
  3. Re-size
  4. Full risk check
  5. Broker preview
  6. Place order

3 · Monitor, every 5 minutes

  1. Reconcile with broker
  2. Circuit breakers
  3. Stop, target and time exits

Pink marks the only step that was ever a model. After the experiment below, even that step is a rule.

Four decisions that matter

  1. The proposer cannot size or send an order

    An independent verifier recomputes what each proposal implies from my own data. It rejects anything ungrounded (every cited evidence ID must exist in this cycle, and the symbol's own price evidence must be cited), stale, priced outside a collar around the quote, with a stop too close or too far in ATRs, without enough reward for the risk, or without edge after costs.

    Position size comes from quarter-Kelly on the stated edge, capped at 2% risk per trade and 6% of equity at risk across all positions. I used a quarter because a model's confidence figures are not calibrated.

    verifier.py · portfolio.py · risk.py

  2. The risk limits are a file the agent cannot write

    Limits live in config/risk_limits.yaml and change only through a human git commit. The file's hash is recorded with every risk decision, so I can tell which limits applied to any trade. Examples: a 5% drawdown breaker, a 2% daily-loss check that blocks new entries, and at most five new trades a day.

  3. Execution is idempotent and never retries blindly

    Client order IDs are derived deterministically from the decision, so a repeated submit finds the existing order. Each order is previewed first, and a preview cost that differs from the intended cost is rejected. If the broker's answer is ambiguous, the order moves to a reconcile state and is resolved by asking the broker, not by sending it again. After a fill, a broker-side stop is placed and re-armed if it goes missing.

    execution.py

  4. The audit trail is tamper-evident, and the kill switch is a file

    The events and evidence tables are insert-only, enforced by SQLite triggers that abort any update or delete. Each event stores the previous hash and its own, so an edit breaks the chain. Tables such as orders and trades are projections that can be rebuilt from the events plus broker history.

    The kill switch needs no access to the running process: create state/KILL and new orders stop, and open entry orders are cancelled on the next pass. Real orders also need three separate switches to be on, so any one being off turns entries into rejections.

    ledger.py · killswitch.py

The experiment: did Claude earn its place?

I replayed 2024 (about 252 trading days) over the 100 most liquid US stocks plus an S&P 500 ETF, starting from $1,500. Both agents ran through the same verifier, sizing, stops, slippage model and kill switch. Before the run I set the bar: the Claude agent had to beat the baseline on both Sharpe ratio and win rate.

Verdict: it failed my rule. The Claude agent's Sharpe lead was 0.03, which is noise, and its win rate was 3.5 points lower. Its one real advantage was roughly half the drawdown. A measured research cycle cost about $0.11, which is about $27 a year, or 1.8% of a $1,500 account, before any benefit.

So I removed the LLM layer, kept the baseline, and kept the harness that told me the truth.

What I would not claim from this

  • It is one year, and 2024 was a strong bull market for the benchmark.
  • It is one run of a nondeterministic model, so a rerun would give different numbers. The Sharpe gap of 0.03 sits well inside that noise.
  • With a $1,500 account, whole-share rounding and fixed order costs affect both agents.
  • An early 49-call partial run showed a 65% win rate for Claude on a handful of trades. I discarded it as statistically meaningless once the full year existed.

What went wrong along the way

  1. My first comparison was invalid. The harness never loaded the API key, so every model call failed. The backtester swallowed the error as "no trade" and printed a fake 0% win rate for Claude. Now the harness loads its configuration, records the first error of each kind, and aborts if a model agent only produces errors.
  2. I killed healthy runs. I was watching the wrong cache directory, so a run waiting on the network looked hung. I stopped it after 40 minutes and stranded about $7.50 of work.
  3. The cache was fragile. Its key included account state that depended on earlier model decisions, so only an identical chain of decisions could reuse it.
  4. I had no visibility into spend. About $13 looked like nothing until I added a spend ledger with a hard cap, an abort after three failures in a row, and a request timeout.

Where it stands

The baseline agent roughly matches SPY in 2024 and does not beat it. I would rather say that plainly than tune until a chart looks good. The system is built to go live one gate at a time: read-only against the broker's test environment, then shadow mode with orders recorded but not sent, then test-environment orders, then live. I will compare each stage against the backtest before adding size.

If I want an edge, the next step is testing other signals inside the same verifier and risk framework, not putting a model back in.
